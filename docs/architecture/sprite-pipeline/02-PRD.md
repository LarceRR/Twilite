# 02. PRD: Sprite Pipeline v2 (production-ready)

> BMAD role: **PM**. Источник: `01-PROJECT-BRIEF.md`. Каждое требование имеет ID; stories ссылаются на эти ID в поле `Covers`.

## 1. Эпики

| Epic | Название | Фаза | Репо |
|------|----------|------|------|
| E0 | Единые контракты и фикстуры | Phase 0 | API (владелец), PG, MOB |
| E1 | Безопасность медиа и модерации | Phase 1 | API |
| E2 | Целостность домена каталога и поверхности | Phase 2 | API |
| E3 | Надёжное авторство в PG | Phase 3 | PG |
| E4 | Production-рендер на мобильном | Phase 4 | MOB |
| E5 | Качество, наблюдаемость, выпуск | Phase 5 | все |

## 2. Функциональные требования (FR)

### E0 Контракты

| ID | Требование |
|----|------------|
| FR-0.1 | Все схемы TPO manifest, DTO, upload ticket, surface binding, коды ошибок, лимиты и realtime-события определены один раз в пакете `@twilite/contracts` (zod 4) |
| FR-0.2 | Пакет экспортирует TypeScript-типы, zod-схемы, константы и golden fixtures (валидные и невалидные) |
| FR-0.3 | API, PG и MOB импортируют схемы только из пакета; ручные копии удалены |
| FR-0.4 | Каждый репозиторий в CI прогоняет fixture-тесты пакета против собственных мапперов/билдеров |
| FR-0.5 | Версионирование пакета по semver; breaking change запрещён внутри `twilite.pixelobject/v1` |

### E1 Безопасность

| ID | Требование |
|----|------------|
| FR-1.1 | Подтвердить загрузку может только владелец ассета; чужой `assetId` -> 404 (не 403, чтобы не раскрывать существование) |
| FR-1.2 | Confirm проверяет объект в R2 (HEAD): существует, `ContentLength == byteSize`, `ContentType == contentType`. Иначе: объект удаляется, ассет -> `rejected`, ответ 422 с кодом |
| FR-1.3 | Сервер никогда не загружает в память объект больше лимита kind; размер проверяется до GET |
| FR-1.4 | Для каждого kind задан allowlist content-type и максимум байт из реестра лимитов |
| FR-1.5 | Применяется `LIMIT_MEDIA_UPLOADS_PER_USER_PER_DAY` (429 `MEDIA_UPLOAD_QUOTA_EXCEEDED`) |
| FR-1.6 | Медиа- и pixelate-маршруты защищены RBAC-разрешениями из каталога и throttler |
| FR-1.7 | Публичный storage key не содержит `userId` |
| FR-1.8 | Все `:id`-параметры валидируются как UUID (400 вместо 500) |
| FR-1.9 | Модератор не может опубликовать/отклонить собственную ревизию (403 `PIXEL_OBJECT_SELF_MODERATION`), если не включён явный override для single-admin окружений |
| FR-1.10 | Модерационные действия пишутся в аудит-лог (кто, когда, ревизия, решение) |
| FR-1.11 | Pixelate по URL защищён от SSRF (redirect, DNS rebinding, приватные диапазоны v4/v6, лимиты размера и времени) |

### E2 Домен

| ID | Требование |
|----|------------|
| FR-2.1 | Каждая отправка создаёт неизменяемую ревизию. Опубликованная ревизия остаётся живой, пока не опубликована следующая |
| FR-2.2 | Каталог (`GET /tpg/pixel-objects`) поддерживает cursor-пагинацию, сортировка по `published_at desc, id desc` |
| FR-2.3 | `GET /tpg/pixel-objects/limits` возвращает публичные лимиты авторства (схема `PixelObjectLimitsDto`) |
| FR-2.4 | Автор и модератор могут архивировать объект; архив исчезает из каталога, но продолжает резолвиться для существующих размещений |
| FR-2.5 | Surface object имеет first-class поле `pixelObjectId` (FK). При создании сервер проверяет, что объект опубликован и не в архиве |
| FR-2.6 | Привязка неизменяема; ключ `pixelObjectId` в metadata зарезервирован и не может быть изменён через PATCH |
| FR-2.7 | Snapshot поверхности и realtime-события `surfaceObject.created/updated` содержат `pixelObject` (embed mobile DTO живой ревизии) или `null` |
| FR-2.8 | Применяются `LIMIT_OBJECTS_PER_SURFACE` и лимиты размера/ключей metadata |
| FR-2.9 | Неподтверждённые загрузки старше 24 ч и неиспользуемые pixel-sheet старше 7 дней удаляются фоновым job |
| FR-2.10 | `POST /tpg/pixel-objects`, `PATCH /tpg/pixel-objects/:id`, `POST /media/uploads` поддерживают `Idempotency-Key` |
| FR-2.11 | При submit сервер генерирует превью PNG (`staticPreviewFrame`, nearest, x4, макс 640 px по стороне) и отдаёт `previewUrl` |
| FR-2.12 | При публикации новой ревизии пространства с размещениями этого объекта получают realtime `pixelObject.revisionPublished` |
| FR-2.13 | Повреждённая запись manifest не ломает весь листинг: строка пропускается и логируется |

### E3 PG

| ID | Требование |
|----|------------|
| FR-3.1 | Кнопка отправки блокируется, если холст > `canvasMax`; доступны действия «уменьшить (nearest)» и «обрезать по центру» |
| FR-3.2 | Экспорт «PNG кадра» экспортирует активный кадр |
| FR-3.3 | Отправка: прозрачные шаги (упаковка -> загрузка -> подтверждение -> отправка), ретрай сетевых шагов, Idempotency-Key, явный экран успеха |
| FR-3.4 | Ресабмит: автор открывает свой объект (rejected/published) в редакторе из sheet + manifest и отправляет новую ревизию |
| FR-3.5 | Каталог «Мои» и очередь модерации постраничные; кнопки модерации своих ревизий недоступны |
| FR-3.6 | Все серверные коды ошибок мапятся на понятные русские сообщения |

### E4 Mobile

| ID | Требование |
|----|------------|
| FR-4.1 | Все ответы каталога/DTO/snapshot валидируются zod-схемами пакета; невалидные записи не рендерятся и логируются |
| FR-4.2 | Источник DTO для поля: embed из snapshot/realtime; fallback `/mobile` для старого API |
| FR-4.3 | Ключ кеша DTO включает `revision`; новая ревизия автоматически подменяет текстуру |
| FR-4.4 | Если спрайт недоступен (загрузка, ошибка, нет привязки) - рисуется placeholder по kind |
| FR-4.5 | Загрузка текстур параллельна (concurrency 3), с ретраями (3, экспоненциально), LRU-бюджет текстур |
| FR-4.6 | Рендер без аллокаций GPU-буферов в кадре; один `bufferData` на кадр |
| FR-4.7 | Потеря GL-контекста и возврат из background восстанавливают слой без перезапуска экрана |
| FR-4.8 | `reduceMotion` замораживает анимацию; в background RAF остановлен |
| FR-4.9 | Карточки каталога используют статичное превью (без GLView на карточку), список виртуализирован и постраничен |
| FR-4.10 | Ошибка создания объекта из каталога показывается пользователю; повтор идемпотентен |
| FR-4.11 | Local sandbox показывает встроенный fixture-каталог |
| FR-4.12 | Мёртвые пути рендера удалены |

### E5 Качество

| ID | Требование |

## 3. Нефункциональные требования (NFR)

| ID | Требование | Проверка |
|----|------------|----------|
| NFR-1 | Валидация sheet на сервере: p95 < 300 ms для 8 MiB / 64 кадров 160x160, пиковая память процесса +< 64 MiB | Бенчмарк-тест в P1-S9 |
| NFR-2 | `GET /spaces/:id/surface` со embed: 1 SQL-запрос на объекты + 1 батч на ревизии (без N+1), p95 < 150 ms для 500 объектов | Интеграционный тест P2-S7 |
| NFR-3 | GL-слой: 0 `createBuffer`/`deleteBuffer` в RAF; p95 paint <= 8 ms для 50 спрайтов на эталонном устройстве | P4-S5, P5-S6 |
| NFR-4 | Память текстур <= 48 MiB оценочно | P4-S4 |
| NFR-5 | Все изменения контрактов в v1 аддитивны; старый клиент не ломается | Contract tests P0-S3 + compat-тест P5-S4 |
| NFR-6 | Каждая ошибка имеет стабильный `code` из реестра | Lint-тест в P0-S5 |
| NFR-7 | Тестовое покрытие изменённых модулей: строк >= 85%, ветвей >= 75% | CI coverage gate |
| NFR-8 | Логи не содержат presigned URL целиком, JWT, cookie | P5-S3 |
