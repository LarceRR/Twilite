# 01. Project Brief: Sprite Pipeline Hardening

> BMAD role: **Analyst**. Входные данные: audit context pack от 2026-10-01 + чтение кода (`master`).
> Downstream: `02-PRD.md`, `06-ADR-LOG.md`.

## 1. Проблема

Пиксельные спрайты проходят через три репозитория (PG -> API -> MOB), но:

1. **Контракты продублированы руками** в трёх местах (`pixelObjects.contract.ts` в API, `src/shared/contracts/pixelObjects.ts` в MOB, `src/shared/api/pixelObjects.ts` + `manifest.ts` в PG). Мобильный клиент не валидирует ответы в runtime (в `package.json` нет zod), PG тоже.
2. **Связь surface object -> pixel object существует только как клиентская конвенция** (`metadata.pixelObjectId`). Сервер не знает об этой связи, не проверяет её и может её затереть (PATCH metadata заменяет объект целиком).
3. **Загрузка медиа имеет дыры безопасности**: confirm без проверки владельца (IDOR), без проверки факта/размера/типа объекта в R2, presigned PUT без ограничения размера, а валидация на submit скачивает объект целиком в память до проверки размера.
4. **Модерация разрушает живой контент**: повторная отправка опубликованного объекта переводит его в `pending`, и все размещения в чужих пространствах теряют спрайт до повторной публикации.
5. **Рендер на мобильном работает, но не production-grade**: аллокации GPU-буферов на каждый quad каждый кадр, последовательная загрузка текстур без ретраев, тихие пропуски спрайтов, отсутствие текстурного бюджета, игнор `reduceMotion`, по одному GLView на карточку каталога.
6. **Лимиты объявлены, но не применяются**: `LIMIT_OBJECTS_PER_SURFACE`, `LIMIT_MEDIA_UPLOADS_PER_USER_PER_DAY`, `LIMIT_MEDIA_IMAGE_MAX_BYTES`, `LIMIT_MOMENT_METADATA_*` не найдены в путях создания (подлежит подтверждению grep-ом, см. 05).
7. **Дрейф лимитов**: PG разрешает документ до 1024 px по стороне, API принимает максимум 160.

## 2. Цели (Goals)

| ID | Цель | Измеримый критерий |
|----|------|--------------------|
| G-1 | Единый источник правды для контрактов | 0 ручных копий типов TPO/DTO в PG и MOB; все три репо проходят одни и те же golden fixtures в CI |
| G-2 | Закрыть уязвимости загрузки | Все SEC High/Critical из 05 закрыты и покрыты регрессионными тестами |
| G-3 | Целостность размещений | 0 размещений, ссылающихся на несуществующий/неопубликованный объект после создания; resubmit не скрывает живой спрайт |
| G-4 | Предсказуемый рендер | На эталонном low-end Android: 50 объектов / 20 уникальных sheets: p95 кадра GL-слоя <= 8 ms, 0 аллокаций буферов в RAF |
| G-5 | Наблюдаемость | Каждая ошибка загрузки текстуры, валидации sheet и confirm видна в Sentry/логах с кодом |
| G-6 | Обратная совместимость | Старые мобильные сборки (пишут `metadata.pixelObjectId`, читают `/mobile`) продолжают работать в течение окна совместимости (ADR-015) |

## 3. Не-цели (Non-goals)

- Процедурный voxel Fire / `SceneView`: не развиваем, только карантин или удаление (ADR-010).
- Темы, градиенты неба, аватары, голос, вложения: только там, где общая медиа-инфраструктура требует исправлений (P1-S1...S4 затрагивают все kinds, это намеренно).
- Мульти-анимации, non-loop анимации, APNG/GIF в каталоге: формат остаётся `v1`.
- Монорепозиторий: репозитории остаются раздельными (ADR-001 решает контракты пакетом).
- Подписанные CDN URL для pixel sheets: каталог публичен по дизайну (ADR-006). Приватность других kinds вынесена в отдельный трек.

## 4. Ответы на открытые вопросы аудита (§16)

Оркестратор принимает решения по умолчанию. Владелец может отменить любое на Gate G0; тогда соответствующий ADR переписывается **до** старта зависимых stories.

| # | Вопрос | Решение по умолчанию | ADR |
|---|--------|----------------------|-----|
| 1 | Холст > 160 для каталога? | **Нет.** 160 - каноничный максимум. PG блокирует отправку и предлагает downscale/crop | ADR-002 |
| 2 | Отклонять неизвестный/неопубликованный `pixelObjectId` при создании? | **Да**, 422 `PIXEL_OBJECT_NOT_PUBLISHED` | ADR-004 |
| 3 | При resubmit опубликованного: старые размещения сохраняют прежнюю ревизию? | **Да.** Живая ревизия остаётся до публикации новой. После публикации все размещения автоматически переходят на новую | ADR-003 |
| 4 | Pending sheet URL публичны намеренно? | Принято как риск (UUID-ключи, immutable). Но из ключа убирается `userId` | ADR-006 |
| 5 | Применять `LIMIT_OBJECTS_PER_SURFACE` сейчас? | **Да**, 409 `SURFACE_FULL` | ADR-013 |
| 6 | Fire/Cloud без sheet остаются валидными? | **Да**, рисуются встроенным placeholder-спрайтом по kind | ADR-010 |
| 7 | GPU-бюджет | 32 уникальные текстуры или 48 MiB оценочной памяти (w*h*4), LRU | ADR-008 |
| 8 | reduceMotion замораживает анимацию? | **Да**, рисуется `staticPreviewFrame` | ADR-009 |
| 9 | IDOR confirm для других kinds - принятый риск? | **Нет, это баг.** Исправляется для всех kinds | ADR-005 |
| 10 | Signed CDN URL? | Не для pixel-sheet/preview. Для voice/attachment - отдельный трек (вне пакета) | ADR-006 |

Дополнительные решения, которых не было в аудите:

| Вопрос | Решение | ADR |
|--------|---------|-----|
| Удаление pixel object | Мягкий архив; архивные объекты продолжают рендериться в существующих размещениях, исчезают из каталога | ADR-007 |
| Удаление аккаунта автора | Опубликованные объекты анонимизируются, а не удаляются каскадом (сейчас `author_user_id ON DELETE CASCADE`) | ADR-014 |
| Привязка спрайта после создания | Неизменяема. Сменить спрайт = удалить и создать объект | ADR-004 |
| Превью в каталоге | Сервер генерирует PNG превью (staticPreviewFrame, nearest x4) при submit | ADR-016 |
| Сетка spritesheet | `rows == ceil(frameCount / columns)`, `1 <= columns <= frameCount` | ADR-011 |

## 6. Метрики успеха (после G5)

- Доля surface objects с `pixel_object_id`, у которых нет живой ревизии: **0**.
- Доля мобильных сессий с ошибкой загрузки текстуры: **< 0.5%** (Sentry event `sprite.texture_failed`).
- Время от появления объекта партнёра (realtime) до первого кадра спрайта: **p95 < 1.5 s** на 4G (embed убирает отдельный запрос DTO).
- Отказы submit из-за дрейфа контрактов (`PIXEL_OBJECT_INVALID_MANIFEST` при клиентской проверке ок): **0**.
